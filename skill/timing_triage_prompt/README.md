# timing_triage_prompt：从布线后时序报告判断"继续调还是改结构"

类型：提示词工作流（与大模型协作时使用）。

## 适用场景

整平台布线后 setup 违例分散在许多端点上，局部 OOC 综合能过、集成后又失败，团队需要决定是继续逐条修路径，还是修改结构。适用于任意 Vivado 工程，不依赖 OFDM。

## 来源（本项目实际经过）

- 10-18 到 10-21 期间做了大量单路径微调，整平台 WNS 从 −1.834 ns 改善到 −0.929 ns，但仍有 14,179 个违例端点。局部 OOC 的收益多次在集成后消失。
- 按"控制结构族"对最差 50 条路径分类后发现，49 条集中在候选队列、票据/仲裁、公共故障分发和搜索控制几类结构上，FFT、均衡等数值模块不在其中（`docs/decisions/2026-10-21_route_assessment.md` 第 1 节）。
- 据此决定保留数值组件，把 RX 捕获/调度改为单条流式流水线（路线 B）。改造后的整平台实现也不是一次成功：`build/pf2` 因约束引用的端口不存在而报错，`build/pf3` 放置后 WNS −5.035 ns；`build/pf4`（10-21）布线后 WNS +0.123 ns。当前候选 WNS +0.113 ns、TNS 0（`evidence/platform/routed_timing.rpt`）。

注意：改造前后的功能范围不完全相同（改造后去掉了多上下文重叠调度和 DMA 载荷链，见设计报告）。因此这条经验能说明的是"判断方法让决策更快、方向正确"，不能说明"同功能节省多少资源"。

## 用法

1. 先自己运行并保存以下报告，不要让模型凭空推测：

   ```tcl
   report_timing_summary -max_paths 50 -file timing_summary.rpt
   report_timing -max_paths 50 -nworst 1 -sort_by group -file worst50.rpt
   report_utilization -hierarchical -file util_hier.rpt
   ```

2. 把报告交给模型，使用下面的提示词：

   > 下面是整平台布线后的最差 50 条 setup 路径和层次化资源报告。
   > 1) 按起点/终点所在的层次模块把路径分组，列出每组的路径数、最差裕量、典型逻辑级数和扇出；
   > 2) 区分"数值数据通路"与"控制/调度/握手"两类；
   > 3) 如果超过一半的违例落在同一类控制结构上，指出这类结构在设计中承担的功能，并给出能消除这类结构、而不是给它加流水线的替代架构；
   > 4) 只引用报告里出现的数字，推测的内容必须标明"推测"；
   > 5) 最后给出"继续微调"和"修改结构"两种方案各自的预计实现轮数与风险。

3. 拿到分类结果后，人工抽查 3–5 条路径的真实起点/终点，确认分类没有错，再做决定。

## 已验证效果

本项目中，一次分类就把方向从"逐条修路径"转为"替换调度结构"。此前 3 天的微调没能消除违例；改结构后，在同一天的第 4 次整平台运行（pf1–pf4，pf1 的结果未留下时序记录）达到无负裕量（见上文来源）。只有这一个项目的一次实例，属于单案例经验。

## 失效条件

- 违例集中在单条路径或时钟约束本身有问题（例如缺少 CDC 例外、生成时钟定义错误）时，分类没有意义，应先检查约束。
- 模型会把报告中的层次名"翻译"成功能，必须人工核对。它也可能在无依据的情况下给出"预计节省多少 LUT"之类的数字，这类数字一律视为推测。
- 修改结构有功能回归的风险：必须有独立的黄金参考（本项目用 Python 模型和向量），才能放心重写。
